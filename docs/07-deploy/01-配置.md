# 7.1 配置

[返回本章](README.md) · [全书目录](../README.md)


服务配置 Go 结构在各自 internal/config，经 svc 初始化依赖；具体配置文件在各服务 etc 或网关旁。
**数据库隔离配置原则**：每个业务服务的配置结构只允许持有本域自身的 `Mysql.DataSource` 与最小权限，禁止塞入他服务 DSN 或共库账号；物理隔离前提见[第 6 章](../06-data/)。
本手册只说明结构与归属，不收录真实数据库、Redis、机器票、对象存储凭据，也不要求 AI 自动打开配置值。
commonconfig 是跨仓地址/RemoteProxy 注册结构，不能误认为可信的公开凭据样本。
新配置：结构/默认值/必填/缺失行为/使用者一起评审；秘密由环境安全注入，日志与说明只写变量名。
缺安全关键配置应失败关闭，不能默认用空密钥或开发 token 继续服务。

### 7.1.1 密钥命名（JWT / S2S 统一带前缀短格式）

前缀只标归属，便于开发期肉眼区分；尾部 32hex 提供 122bit 熵，不要用可读单词代替。

| 类型 | 格式 | 例子 |
|---|---|---|
| JWT | `beaver-jwt-{user\|open\|admin}-{32hex}` | `beaver-jwt-admin-…` |
| S2S 入站验票 | `beaver-s2s-{签发方}-{32hex}` | `beaver-s2s-ai-…`（ai 仓自己的 `S2S.Secret`） |
| S2S 换票凭据 | `beaver-s2s-{签发方}-{接收方}-{32hex}` | `beaver-s2s-observability-backend-…` |

- “签发方”是**签发这张机器票的团队**（持有 machine token 端点的一方），“接收方”是**拿票来调用的服务**。
  例：`RemoteProxy.Beaver.ClientSecret` 形如 `beaver-s2s-core-backend-…`，即 core 签发、backend 接收。
- `S2S.Clients` 的**键**是调用方 yaml 里的 `Name`（如 `backend_admin`），**值**必须与对端 `RemoteProxy.<团队>.ClientSecret` 逐字一致；改一侧必须同步另一侧，否则验签失败。
- 命名不符合本格式的密钥一律视为待修配置，不要以“能跑”为由保留。

### 7.1.2 RemoteProxy 为什么按团队而不是按服务分组

`RemoteProxy` 的子键是**团队**（`beaver`/`social`/`doc`/`open`/`ai`/`observability`），团队下再是 `ClientSecret` + `Services` 服务地址表。

- 因为 `client_credentials` 换来的机器票**受众是团队级**（如 `core:api`、`ai:internal`），一张票能打该团队下所有服务；密钥因此也只能是团队级。
- 服务粒度已经体现在 `Services` 的 key（`account`/`relation`/`message`/…）。若把密钥下沉到服务级，等于同一团队存 N 份相同密钥，轮换要改 N 处，且与“一票通团队”的受众模型冲突。
- 加服务只改 yaml 的 `Services`；加团队才改 `commonconfig` 结构体（go-zero 强类型绑定不收未知键到 map）。
